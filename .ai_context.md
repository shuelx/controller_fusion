# Contexto del proyecto: controller_fusion.py

Este archivo es para que una IA (o el usuario mismo en otra sesión/equipo)
retome el proyecto sin tener que releer todo el historial de chat. Está en
español porque así se trabajó la conversación; el código en sí está en inglés.

Está guardado como `.ai_context.md` (con punto adelante) a propósito, para
que quede como archivo oculto en vez de aparecer como documentación
prominente en el repo — pedido explícito del usuario, no es un descuido de
nombre.

## Qué es esto

El usuario y sus amigos (4 a 6 personas) quieren jugar **Ultimate Marvel vs
Capcom 3** en un solo PC, cada uno con su propio mando Xbox 360 (conectado
como mando virtual vía **Parsec**, algunos son fightsticks), pero
controlando **un solo equipo entre varios**: cada amigo maneja un personaje
distinto del mismo team, o se arma 2v2/3v2/3v3 (dos lados, cada lado con
2-3 amigos compartiendo un control).

UMVC3 solo puede leer hasta 4 mandos vía XInput, así que la solución es
**fusionar** N mandos físicos en 1 o 2 mandos **virtuales** que el juego ve
como si fueran mandos normales.

## Stack técnico

- **Windows only.**
- Lee los mandos físicos con **pygame** (backend SDL2), no con la librería
  XInput directa (SDL puede leer más de 4 dispositivos, XInput clásico no).
- Crea el/los mando(s) virtual(es) con **vgamepad**, que usa el driver
  **ViGEmBus** (mismo driver que usa Parsec por debajo). vgamepad instala
  ViGEmBus la primera vez que se usa.
- **NO se usa vJoy.**
- GUI hecha con **tkinter** puro (stdlib, sin librerías de UI de terceros -
  se probó sumar `sv-ttk` para un look más moderno y se **revirtió**, ver
  sección de bugs más abajo).

## Repo

Subido a GitHub, **repo privado**: `github.com/shuelx/controller_fusion`.
Hay un tag `pre-gui` marcando el último commit antes de que existiera la
GUI, por si alguna vez hay que volver a la versión solo-texto que se sabe
que anda. El usuario está aprendiendo a manejar git de a poco (se lo guié
paso a paso al principio); en sesiones recientes ya hace el
`add`/`commit`/`push` solo.

## Archivos del proyecto

- `controller_fusion.py` — todo el motor + CLI + GUI, un solo archivo.
- `latency_probe.py` — mide el lag que agrega el pipeline propio (lectura +
  escritura), standalone, se puede correr sin la GUI.
- `setup.bat` / `setup.ps1` — doble-click para quien no tiene Python:
  detecta si hay un Python 3.9+ que funcione de verdad (no el alias trucho
  de la Microsoft Store), lo instala vía `winget` si falta, si eso también
  falla abre la página de descarga y explica qué hacer. Nunca deja a nadie
  colgado. Al final arranca `--gui`.
- `play.bat` — lanzador directo sin chequeos, para cuando ya está todo
  instalado (`python controller_fusion.py --gui` sin abrir consola).
- `README.md` — documentación pública del repo (en inglés, sin mencionar
  el sistema de chistes internos, a pedido del usuario).
- `profiles.json` / `session.json` / `logs/` — datos generados en uso, NO
  se versionan (están en `.gitignore`). `profiles.json` se llena de basura
  de calibración con nombres random (`guasa`, `tubi2`, etc.) cada vez que
  el usuario prueba fightsticks nuevos — es normal, no hace falta limpiarlo
  a menos que él lo pida.

## Comandos (CLI, sin GUI)

```
python controller_fusion.py --list                      # lista mandos detectados
python controller_fusion.py --diagnose N [seg]           # loguea ejes/botones (calibracion)
python controller_fusion.py --identify                   # cada persona aprieta un boton, ve que indice es
python controller_fusion.py --profile-create N [nombre]  # wizard: crea un perfil para el mando N
python controller_fusion.py --profile-list                # lista perfiles guardados
python controller_fusion.py --setup                       # wizard de texto: asigna P1/P2 + perfil, arranca a jugar
python controller_fusion.py --gui                         # la GUI, ver mas abajo
python controller_fusion.py                                # corre con session.json si existe, si no con CONFIG
python latency_probe.py N [seg]                            # test de latencia standalone
```

Dependencias (`pygame`, `vgamepad`) se auto-instalan solas (`_ensure_package`
al principio del archivo) — si falla, avisa exactamente qué falta, no queda
colgado ni tira traceback crudo. `--gui` además chequea `vgamepad` y
`tkinter` por adelantado, antes de abrir la ventana.

## La GUI (`--gui`) — qué tiene

Ventana única (con dos ventanas secundarias: editor de perfiles y test de
latencia). Todo pensado para no romper el mecanismo de arrastre, que ya se
rompió más de una vez durante el desarrollo por cambios aparentemente
inocentes (ver bugs abajo).

- **Tarjetas** por cada mando detectado: nombre editable, diagrama de mando
  en vivo (dibujado a mano con `Canvas`, no es una imagen — ver
  `_draw_pad_diagram`/`_update_pad_diagram`), selector de perfil, botón ⚙
  para el editor de perfiles. Se arrastran entre un "pool" (sin asignar) y
  las zonas P1/P2.
- **Diagrama de mando**: dpad, 4 botones de frente, hombros, gatillos,
  back/start, y **ambos sticks con movimiento real** (un punto que se mueve
  dentro de un cuadrito, no solo prende/apaga) + L3/R3. Reusa el mismo
  perfil que tiene seleccionado esa tarjeta, o sea que si el perfil es
  custom, el diagrama muestra la traducción real, no el input crudo.
- **Pool con scroll**: si hay más mandos de los que entran en una pantalla
  chica (720p), aparecen flechas ▲▼ (y rueda del mouse) — pero SOLO cuando
  hace falta, se ocultan si todo entra.
- **Start/Stop** (antes "Go live"): NO es un botón de un solo uso que cierra
  la ventana — es un toggle. Arranca apagado a propósito (nadie manda input
  sin querer mientras se arman los equipos). Mientras está prendido,
  **arrastrar tarjetas entre P1/P2 remapea en vivo**, sin reiniciar nada.
  Los mandos virtuales se crean recién al primer Start (lazy), y **se
  desconectan de verdad al apretar Stop** (ver bug de pad no liberado).
- **Refresh**: re-escanea mandos conectados/desconectados. Solo funciona
  con Stop apretado (deshabilitado en vivo) — a propósito, para no meter
  ninguna revisión automática en el loop de 4ms que sí importa para el lag.
  No resetea todo: solo agrega/saca tarjetas de lo que cambió.
- **Editor de perfiles** (⚙ en cada tarjeta): crear/editar/borrar un
  perfil, con un tester en vivo (botones + ejes) integrado, sin bloquear la
  ventana principal (usa su propio polling, pausa el de la ventana
  principal mientras está abierto para no pelearse por los mismos eventos
  de pygame).
- **Combined view** (columna angosta a la derecha, siempre visible): dos
  diagramas chicos mostrando lo que P1 y P2 reciben YA MEZCLADO entre todos
  los que están en ese lado — para validar "estoy en el lugar correcto".
  Al principio se probó como ventana aparte y se sacó porque se podía abrir
  2 veces por error; ahora vive embebida, sin ese riesgo.
- **Latency test**: mide cuánto tarda el pipeline propio en escribir una
  apretada al mando virtual. **Muestra SOLO el tiempo de "convert"** (no
  incluye el tiempo de sondeo/espera) — hubo bastante ida y vuelta sobre
  esto, ver sección de decisiones. No mide USB/Parsec/el juego, eso queda
  explícito en la propia ventana.
- **Chiste interno**: cuando se aprieta un botón fuera de "live", el status
  bar dice `" ese fue el gamepad N MAMAAAAAA"` en vez de un mensaje
  genérico — pedido explícito del usuario, no es un bug aunque una revisión
  de código lo señaló como sospechoso. El usuario quiere sumar más frases
  random ahí, pero está esperando pasarlas él mismo — no inventar frases
  sin que él las traiga.

## Decisiones de diseño importantes (el "por qué")

1. **Equivalencia de botones Xbox <-> PlayStation**: A=Cross, B=Circle,
   X=Square, Y=Triangle, LB=L1, RB=R1, LT=L2, RT=R2, BACK=Select,
   START=Start, LS=L3, RS=R3.

2. **Botones obligatorios** para crear un perfil: Cross, Square, Triangle,
   Circle, **L1, R1**, Select, Start. Opcionales (se eligen uno por uno):
   L2, R2, L3, R3. (Hubo confusión en su momento sobre si eran R1+R2 o
   L1+R1 — quedó confirmado L1+R1 por el usuario, no volver a dudarlo salvo
   que él lo cambie.)

3. **Perfil "standard"**: implícito, no se guarda en `profiles.json`, es el
   mapeo por defecto sin remapear nada. Se le puede poner nombre igual (sin
   apretar botones) solo para identificar quién es quién en el resumen.

4. **"merge" en vez de "switch"**: cada amigo controla un personaje del
   mismo equipo funciona mejor con OR lógico entre fuentes, porque el juego
   solo lee al personaje activo en pantalla, y ese input viene de quien
   esté jugando en ese momento.

5. **Índices de mandos físicos NO son estables** entre sesiones de Parsec.
   `--identify` / el flash de las tarjetas / el diagrama en vivo existen
   específicamente para esto — SDL no da nombres útiles, todo aparece como
   "Xbox 360 Controller" sin distinción.

6. **Dpad y sticks nunca se remapean por perfil** — siempre el layout fijo
   de `AXES`. Solo los botones (incluyendo L2/R2 como gatillos) pasan por
   el perfil.

## Bugs reales encontrados y resueltos (con lección)

1. **Botón "pegado" por eje mal capturado en un perfil**: un gatillo (que
   descansa en -1.0, nunca pasa por 0) quedó asignado a un botón normal
   durante la calibración, y como el código interpretaba "apretado" con
   `abs(valor) > 0.5`, daba true todo el tiempo. Fix real: la fórmula para
   ejes mapeados a botones normales pasó a ser `valor > 0.5` (sin `abs`),
   ya que solo el lado positivo del rango significa "apretado". **Lección**:
   correr `--diagnose` antes de armar un perfil custom - si el layout ya es
   estándar, no hace falta perfil custom y se evita este tipo de error.

2. **Mando virtual no se desconectaba al apretar Stop**: `release_pad()`
   solo neutralizaba el pad (lo dejaba en reposo) pero lo mantenía
   conectado — seguía ocupando un slot de XInput y se acumulaban entradas
   fantasma en `joy.cpl`. Fix: ahora limpia la referencia
   (`virtual_pads[side] = None`) para que el `__del__` de vgamepad
   desconecte el dispositivo de verdad. Mismo bug estaba en la ventana de
   Latency Test (su pad de prueba tampoco se soltaba al cerrar) - mismo fix.

3. **Scroll del pool con rueda del mouse no funcionaba en el 90% del área**:
   estaba atado solo al frame `pool`, pero las tarjetas (hijas de `root`,
   no de `pool`) tapan casi toda esa superficie y absorben el evento antes
   de que llegue. Fix: en vez de atar el bind a un widget, se chequea la
   posición de pantalla del mouse contra el rectángulo del `pool`
   (`root.bind_all` + comparación de coordenadas), sin importar qué widget
   esté debajo del cursor.

4. **Se probó `sv-ttk`** (librería de tema visual, Windows 11 Fluent look)
   para el "next level" de pulido visual, y **se revirtió**: el tamaño de
   los botones del header no respetó el layout de píxeles fijos que ya
   había, y quedaron pisándose entre sí. Se volvió al tema nativo de
   Windows (`vista`/`xpnative`/`clam`), que ya estaba confirmado andando
   bien. Queda el helper `_try_ensure_optional` (instala sin nunca tirar
   abajo la app si falla) por si se retoma esto más adelante, pero
   **NO se está usando actualmente**. Lección: cualquier cambio de tema/
   estilo en la GUI necesita verificación visual real (captura del
   usuario) antes de darlo por bueno, no alcanza con que compile y abra.

5. **La ventana de Latency Test mostraba "wait + convert" como un solo
   número** ("extra lag"), y al usuario le resultó confuso — pensaba que
   el número relevante era solo la parte de "convert" (lo que tarda el
   código en escribir al mando virtual), no el tiempo de espera del
   sondeo. Hubo una ronda de explicación técnica (el "wait" técnicamente
   SÍ es lag que agrega el script, no algo que iba a pasar igual) pero el
   usuario prefirió simplicidad ante todo: **la decisión final es mostrar
   SOLO el tiempo de "convert"**, sin mezclar con el wait. No revertir esto
   sin que el usuario lo pida explícitamente - ya se discutió a fondo.

## Cosas que se evaluaron y se DESCARTARON a propósito (no reabrir sin que el usuario lo pida)

- **HidHide**: iba a resolver que el juego vea mandos físicos de más
  (podía superar el límite de 4, o alguien apretaba Start en el mando
  equivocado). El usuario decidió que el workaround manual actual (nadie
  toca Start de más, solo uno por lado) ya alcanza, y no quiere sumar una
  dependencia de sistema para algo que no está roto. Cerrado.
- **Diferenciar visualmente fightstick vs pad** en el diagrama: se planteó
  un diseño (checkbox "esto es un fightstick" en el editor de perfiles,
  el diagrama deja de dibujar los sticks si está marcado) pero el usuario
  decidió que no suma lo suficiente. No implementado.
- **Movimiento del stick derecho**: sí se terminó implementando (mismo
  mecanismo que el izquierdo, adaptado a menos espacio disponible).

## Estado actual / cómo retomar

La carpeta de pendientes está prácticamente vacía. Lo único abierto es un
sistema de frases random tipo el chiste de "MAMAAAAAA" (el usuario va a
pasar las frases él mismo, no inventarlas). Todo lo demás de esta ronda de
trabajo (GUI completa, bugs, backlog) quedó cerrado.

Para retomar en otra máquina/sesión:
1. Clonar el repo privado (`github.com/shuelx/controller_fusion`) o copiar
   la carpeta.
2. Si no hay Python: doble-click en `setup.bat`.
3. Si ya hay Python: `python controller_fusion.py --gui` o doble-click
   `play.bat`.
4. Si el pedido es "mejorá la GUI más": el techo de pulido gratis en
   Tkinter puro ya se tocó (paleta de colores, `ttk` en vez de `tk` crudo,
   bordes, hover). Ir más allá de ahí implica dibujar las tarjetas a mano
   en `Canvas` en vez de `Frame` (mismo riesgo que romper el drag, más
   grande) - ahí es donde una librería de tema se justifica, pero ya se
   probó una (`sv-ttk`) y se revirtió por romper el layout del header sin
   que se pudiera verificar visualmente antes de aplicarlo. Cualquier
   intento nuevo en esa dirección necesita confirmación visual real del
   usuario en cada paso, no asumir que "compila y abre" alcanza.
